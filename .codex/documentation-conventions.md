# STP 文档编写约定

生效日期：2026-10-20。来源：用户在 STP 会话中确认的文档整理约定。

## 1. 组织原则

采用循环：**准备工作 → 实验 → 本轮总结归档 → 更新下一轮准备工作**。

项目同时维护“当前工作文档”和“历史迭代记录”。准备工作与实验部分面向当前方案重新整合编写；总结负责保存旧方案、旧实验及方案演变的因果关系。

| 部分 | 定位 | 应包含的内容 |
| --- | --- | --- |
| 准备工作 | 最新有效方案 | Idea 分析、已有证据、待解决问题、实验协议、实现 Spec；标明当前方案版本及来源总结 |
| 实验 | 最新方案的实现与验证 | 功能级代码修改、tkdiff／diff、环境与参数、执行记录、验证结果和实验结果；关联对应方案与协议版本 |
| 总结 | 历次迭代归档 | 当时的 idea、实现与实验、证据支持范围、可行性判断、修改原因、下一轮方案形成过程 |

这是文档职责约定，不要求将所有文件立即迁入三个同名目录。现有 `experiments/`、`reviews/` 等目录可以继续使用；各文档标明所属类别。历史总结统一从 [总结索引](history/README.md)进入。

## 2. 当前准备工作与实验文档

当前文档应清楚说明本轮问题、方案、边界与待办。旧方案只保留理解当前选择所需的简要说明，并链接历史总结；不要把历次讨论直接拼接成当前 Spec。

实验协议变化时，先标明新版本及变更原因，再说明旧结果是否仍适用。影响结果解释的变化包括量化配置、Selector 路径、Top-k／Top-p 定义、模型、数据、上下文长度和计算／访存统计口径等。

代码修改按功能组织，使用以下表格；多个文件共同实现同一功能时合并说明：

| 功能 | 修改前 | 修改后 | 涉及文件／diff | 验证结果 |
| --- | --- | --- | --- | --- |
| 具体功能或行为 | 原有行为或尚未实现 | 当前行为与目的 | 文件、版本及对应 diff 链接 | 检查范围、结果或尚未验证 |

表格之后列出可复现的环境、命令、参数、输入来源和结果路径。完整 diff 作为附件链接，不用完整 diff 代替功能解释。

每个实验明确记录以下状态，可以同时描述不同层面的进度：

| 状态 | 含义 | 必需说明 |
| --- | --- | --- |
| 规划 | 已设计，尚未完成实现 | 目标、协议、待实现项 |
| 实现 | 已有代码或配置 | 文件／diff／版本、尚未运行的部分 |
| 执行 | 已实际运行 | 环境、输入、命令、日志和原始输出 |
| 验证 | 已对特定性质或结果完成检查 | 检查方法、通过／失败、适用范围及未验证项 |

例如，“FP→INT8 已实现，CPU 局部数值检查通过，完整模型 PPL 与 Top-k／Top-p 对比尚未执行”应分别记录，不能概括为“第一步实验已完成”。统计量、理论估算、仿真结果、硬件实测也要分别标明。

## 3. 历史关联：每轮总结的必需内容

总结使用稳定编号 `R001`、`R002` 等；同一天可以有多轮，一轮也可以跨多天。编号在还原真实顺序后分配，不能把每个文件或每次对话自动视为一轮。

每轮总结回答：

1. 当时的 idea 和目标是什么？相对前一轮沿用或改变了什么？
2. 实现了什么，实际执行了哪些实验？哪些仅规划或实现？
3. 结果支持什么结论，适用范围是什么，哪些问题仍未验证？
4. 为什么修改或保留 idea？具体依据是哪项结果、文献、代码事实或用户决策？
5. 下一轮方案如何形成？保留、修改或放弃哪些内容，需要补哪些证据？

总结开头保留以下关联表。未发生的后继标为“待形成”，无法确认的历史标为“待核实”，不适用项说明原因。

| 关联项 | 内容要求 |
| --- | --- |
| 轮次与时间 | 稳定编号、覆盖时间、归档日期 |
| 前序 | 前序总结链接；首轮明确标注首轮，未知则待核实 |
| 当时方案 | Idea／Spec 与实验协议的固定版本链接 |
| 实现 | 代码基线、修改版本、功能说明、tkdiff／diff；无代码时说明不涉及 |
| 执行依据 | 环境、参数／配置、日志、原始结果、验证记录的固定版本链接 |
| 后继 | 后继总结链接；尚未归档时链接下一轮准备工作及其版本 |

历史记录需要形成可双向追溯的链：

**前序总结 → 本轮方案／Spec → 本轮实现与实验依据 → 本轮判断与修改原因 → 下一轮准备工作 → 后继总结**。

链接之外，还要写清楚方案演变的原因。推荐在“下一轮如何形成”处记录：

| 来源结论／问题 | 对应证据 | 本轮决策及原因 | 下一轮具体变化 | 证据继承范围／重验要求 |
| --- | --- | --- | --- | --- |
| 前序或本轮发现 | 结果、日志、文献或决策记录链接 | 保留／修改／放弃及理由 | Spec／协议的具体变化与链接 | 哪些仍适用，哪些失效或待重验 |

新建后继轮次后，回填前序总结的后继链接，并更新总结索引。若存在并行探索，分别注明来源和分支关系；合并方案时关联所有实际来源，不强行排成单一时间链。

## 4. 历史版本与证据边界

- 使用归档副本、Git 提交编号／固定链接、带版本的配置和结果等保存当时状态。未提交的实现可以关联保存的 patch、代码基线及文件清单，明确标注未提交。
- 只有会随当前方案覆盖更新的链接，不足以支撑历史总结。当前准备工作更新前，先保存本轮引用的版本；归档总结链接该版本。
- 原始日志和结果保留；失败、负面结果和未完成项如实记录。后续更正追加日期、原因与新证据，不静默改写当时结论。
- 旧实验只能支持其实际验证的配置与结论。新方案引用旧证据时说明适用部分；涉及机制或口径变化的部分列为待重验。
- 已有历史材料先核对内容、代码版本和执行依据，再还原迭代顺序。文件名日期仅作线索，证据缺口明确标记。

## 5. 每次文档交付的检查

1. 当前方案是否明确，准备工作和实验文档是否一致？
2. 规划、实现、执行、验证是否分清，结论是否链接到对应版本证据？
3. 若本轮归档，是否回答五个问题并保留当时方案及实验依据？
4. 前序与后继是否关联，修改原因和旧证据适用范围是否写清？
5. 总结索引与当前入口是否同步更新？

论文正文、图表和简短回复按各自体裁输出，不必机械套用全部表格；其研究依据仍通过以上工作文档与历史记录追溯。
